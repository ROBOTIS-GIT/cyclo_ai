# Configuration transaction

Source tables: [XL330-M288](https://emanual.robotis.com/docs/en/dxl/x/xl330-m288/#control-table-of-eeprom-area), [XM430-W350](https://emanual.robotis.com/docs/en/dxl/x/xm430-w350/#control-table-of-eeprom-area), [Protocol 2](https://emanual.robotis.com/docs/en/dxl/protocol2/). The executable registry is separate from retrieved content.

1. Establish the user's requested operation and destination. Resolve electrical interface, adapter and port, protocol, model number, exact firmware, current ID/baud and isolated single-device bus. Use fixtures when live access is outside the task. An authorized installation may discover ports, then scan explicitly selected ports/IDs/rates. Port metadata identifies an adapter, not the actuator. Several devices, mixed rates or no reply are not permission to guess.
2. Plan a bounded scan. `dynamixel_scan` defaults to dry run; its unique ID/rate matrix must fit a 100–15000 ms cooperative budget, 10–200 ms probe timeout, at most 253 IDs and 8 curated baud rates. It returns completed probes and errors. Budget excludes any unbounded OS open delay; it is not a hard process deadline. Cancel stops further probes after an in-flight request completes. Protocol 1, duplicate IDs, secondary listeners, unsupported rates and silent devices may be missed. “No response” is not proof of an empty bus.
3. Select one explicitly confirmed session target or operator-configured target. A port-only bus can supply the preceding bounded scan without a known identity. The configuration must attest physical single-device isolation and exclusivity. A destination-ID probe is an additional collision check, not sufficient proof on its own. Duplicate physical devices sharing an ID cannot reliably be distinguished by ping; isolate them first.
4. Validate the dry-run request. It does not invent a snapshot or certify device compatibility. Real execution re-pings and reads model, firmware, ID, baud, protocol, secondary ID, torque, drive/operating mode, velocity limit and affected registers. Model or firmware mismatch, Protocol !=2, active secondary ID or torque already on stops before writes. The tool never turns torque off or on. EEPROM ID/Baud/Drive Mode require torque off; this plugin also requires it for RAM profile/LED preparation as a conservative policy.
5. ID and baud changes are separate transactions. Before ID write, probe the destination. Change once, verify identity/readback at the new ID. For baud, write its model-specific enum once, confirm old connection closure, open the new rate and verify identity/readback. Lost ACK may still be successful if readback verifies; never blindly repeat or auto-rollback. Store the returned actual location and update the operator target explicitly for later calls. The module updates its session handle only after verified readback, full supported-snapshot continuity, confirmed closure and released reservation. It never silently rewrites operator config. Failed/uncertain operations block further writes until explicit fresh selection; see [first use](../../../references/first-run.md).
6. Profile: establish currently supported position mode. Time uses total/acceleration milliseconds with acceleration <= half total; conservative maximum 32737 follows the narrower published time range. Velocity uses RPM and RPM/min (rev/min²), with explicit positive application maxima. Conversion rounds down to 0.229 RPM and 214.577 rev/min² ticks and reports actual raw values; zero/infinite and below-resolution values are rejected. The observed Velocity Limit is an extra conservative plugin ceiling, not a claim that all firmware uses it to bound position profiles. Time alone does not bound speed without distance/load; do not promise it does. Preserve reverse bit; reject torque-on-by-goal; change only the profile-selection bit if necessary while torque is off. Do not change operating mode or send goals.
7. Save snapshot, requested values, acknowledged errors, readback and closure status. Partial/mismatched/interrupted ID/baud results are `uncertain`, with old/new location candidates for later read-only reconciliation. A close failure retains the bus reservation and prevents reopening. No automatic retry, reconnect after uncertain closure or rollback writes. A cooperative lease does not stop unrelated software; operator must stop other bus owners before execution.

Success is verified register state plus confirmed transport closure, not proven motor behavior. Every result must identify whether it came from mocks or a real operator-authorized session. This release has only mock runtime evidence.
