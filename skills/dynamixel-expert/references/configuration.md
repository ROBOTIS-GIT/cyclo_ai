# Source-bound configuration transaction

Use the complete [typed catalog](../../../references/control-tables.json), [runtime boundaries](../../../modules/dynamixel/README.md) and [official source procedure](../../../references/dynamixel-evidence.md). Every model uses the same engine; capability evidence and task authorization are separate.

For a custom/unindexed device or external table, use the [custom-table procedure](../../../references/custom-control-tables.md). The numbered catalog/MCP steps below do not require inventing a catalog match or rejecting a source-resolved custom operation.

1. Establish the requested named operation: ID is not baud. Confirm electrical interface/adapter, port, intended target and effect. Documentation-only requests never touch ports. Discovery needs a permitted port-only bus, bounded IDs/rates/protocols and an explicit read-only request. Port identity describes an adapter, not the actuator.
2. Dry-run `dynamixel_scan` first. Choose Protocol1 and/or2, at most253 distinct IDs0..252, eight documented rates,10–200ms packet timeout and100–15000ms budget. The matrix budgets up to three identity packets per endpoint. The SDK bridge has a separate per-RPC deadline; OS closure uncertainty retains the lease. Zero replies do not prove absence; show completeness/errors and unscanned scope.
3. Distinguish presence from identity. Protocol1 Ping has no model payload: read model0:2 separately, then use its exact catalog firmware address. Protocol2 Ping includes model/firmware, verified against the model's firmware register. XL-320 uses firmware2 despite Protocol2. MX generation is selected by model number, not protocol. Unknown firmware/identity or a failed READ is unresolved, never a guessed address or a reason to change Status Return Level.
4. Ask for exact catalog identity when a number has multiple document candidates. Preserve marketed aliases without claiming the connector can be electronically distinguished. For dual-axis modules require both actually observed endpoint IDs, explicit cohort confirmation on the selected bus, without requiring other motors to be disconnected; never guess ID+1. Read both identities, protocols, rates, shadow IDs and torque states. A scan cannot exclude duplicate physical IDs or hidden secondary listeners. Ask the operator to verify unique addressing for the selected port/protocol/baud/ID and intended destination; use `addressingVerified:true` only after that confirmation. Resolve ambiguity before writes, using physical separation only when necessary to identify conflicting devices.
5. Select one explicit session target with `dynamixel_select`; include `catalogId` when ambiguous and `peerIds` for dual-axis units. Selection cannot expand scan-only permission or change a target-specific grant's identity/protocol/cohort. Expired observations or changed binding need fresh identification. No candidate is automatically selected.
6. Dry-run `dynamixel_configure` and inspect operation-specific metadata using `dynamixel_registry({catalogId:...})`. The default registry response summarizes all models; exact lookup exposes register evidence and capability conditions. An absent/unresolved capability blocks that operation, not the whole model. Confirm values and effect if still missing authorization. The executor rechecks model/firmware/protocol/table identity, secondary-listener conflicts, verified addressing, applicable torque requirements, memory/lock/mode conditions and applicable limits. It never changes torque.
7. ID and baud changes are separate. Probe the destination ID for any responder before writing. Baud uses that model's documented enum; preflight the actual SDK's host-baud support before writing. Write once, verify the new location and supported snapshot/cohort continuity. A lost ACK can be reconciled by successful reads but never a repeated write. Successful closure and released reservation are required before the session target advances. Config files are never silently rewritten.
8. LED: ask intended color for RGB channels or XL-320 mask. Use `{red:32,green:0,blue:0}` for explicit RGB, `{mask:1}` for an explicit XL-320 mask, or0/1 for binary LED. Off may clear all channels. No writable LED row means unsupported; do not invent an address from a sibling. Alarm/shutdown may override visible output even when the register reads back correctly.
9. Profiles: ask intended behavior, existing Operating/Drive Mode, time versus velocity, physical units and application limits. Do not change mode to satisfy the request. The current resolved X/MX2 templates use0.229rpm and214.577rpm/min or1ms, exact caller-based current-position applicability and firmware gates. Values round down; zero/infinite and below-resolution values are refused. Time acceleration must be at most half total. Device Velocity Limit is an additional conservative ceiling. Other profile layouts remain precisely unsupported/unresolved until their source conflicts/conditions are resolved; never substitute a goal/speed register. No motion is sent to test settings.
10. Return observed register snapshots, requested/raw/actual values, source locations, ACK errors, transport/lease status and runtime evidence level. Any failed/interrupted/mismatched result blocks further writes. After confirmed closure and exclusive ownership, inspect old/new candidates once read-only and select anew. No blind retry, automatic reconnect after uncertain closure, rollback writes, reset or reboot.

Success means verified register state, not motor safety or physical behavior. This release has only offline/mock runtime evidence. Sources: [Protocol1](https://emanual.robotis.com/docs/en/dxl/protocol1/), [Protocol2](https://emanual.robotis.com/docs/en/dxl/protocol2/), and per-model pinned citations in the typed catalog. Do not copy one series' addresses, units or firmware gates to another.

Live port listing, scans and configuration require `confirmed:true` after user approval for that exact call; scan/configure retain `dryRun:true` by default. ID changes probe the destination at the current baud; baud changes probe each affected endpoint at the destination rate before writing. Incomplete scans never establish unique addressing. Neither an ID-keyed scan result nor a successful ping proves no duplicate or secondary listener exists.
