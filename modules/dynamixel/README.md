# Generic DYNAMIXEL product module

`cyclo-products` owns customer-facing documentation, discovery, explicit target selection and named configuration. One identity/capability engine uses `references/control-tables.json`, compiled offline from the pinned official model tables. Freshly retrieved prose can never supply a writable address. The separate retained Cyclo firmware MCP remains pinned and unchanged.

## Coverage and boundaries

| Layer | Implemented scope | Evidence |
| --- | --- | --- |
| Catalog | 89 actuator documents across AX/DX/EX/MX/P/PRO/RX/X/Y; three DYD mechanical documents | Full source inventory and independent table-row witnesses |
| Identity | Bounded unicast Protocol 1/2; exact model-number candidates, model-specific firmware reads | Official SDK packet tests on fake byte ports; no physical ports |
| ID / baud | Source-bound per-model rows and baud enums; communication transition/continuity checks | All 89 records exercised through one in-memory engine |
| LED | Binary, explicit XL-320 color mask, explicit RGB channels; missing LED is unsupported | 84 records have LED metadata; five XW records lack writable LED rows |
| Position profiles | Resolved X/MX2 shared components with exact caller/firmware/mode conditions | 38 records; other 51 profiles are absent or unresolved, never substituted with speed/goal writes |
| Transport | Unmodified Apache-2.0 DynamixelSDK Python 3.8.4 packet/port implementation | Pinned source hashes; fake checksum/CRC/status/error and stdio tests |

Document counts are not every physical variant, exhaustive semantic certification or hardware acceptance. Numeric identities1070,1080,1270 map to multiple documents: require an exact catalog selection; do not guess the marketed variant/connector. Original MX and MX(2.0), PRO R and R(A), XL-320, dual-axis units and Y/Modbus retain distinct metadata. Protocol alone never selects the table generation. DYD has no serial identity.

Protocol 1 Ping establishes presence; the model READ is separate, and firmware is then read at the model's actual address. A blocked identity READ is reported as present-but-unidentified, never an empty bus. Protocol 2 Ping retains its model/firmware payload; when READ replies are available the firmware table read must agree. Typed no-response can retain Ping identity, while CRC/status/identity errors are not treated as suppressed replies. Unknown identities remain documentation queries; the engine does not guess their addresses. A scan cannot prove no duplicate IDs, and only explicitly bounded IDs are probed. ID253 is accepted only for Protocol1 scans and models whose canonical ID contract permits it; the protocol does not determine the model generation.

## Optional future operator runtime

Hardware tools are available by default in both hosts, with no startup serial I/O. `CYCLO_OFFLINE=1` disables both modules; legacy module flags set to `0` also disable the respective module. No Python/serial dependency is required for documentation or mock tests. For a separately authorized real session, prepare a local Python environment using `python3 -m venv /operator/chosen/venv` and `/operator/chosen/venv/bin/python -m pip install -r modules/dynamixel/requirements.txt`. Review dependencies first; no global installation is performed. Set `CYCLO_PRODUCTS_PYTHON` to that interpreter. The product provider uses its private `sdk_bridge.py` with the pinned official SDK under `sdk-upstream`; it does not depend on the retained firmware SDK's generated TypeScript runtime. The original firmware MCP/CLI lifecycle is unchanged.

Python SDK3.8.4 supports only its explicit host-baud set:9600,19200,38400,57600,115200,230400,460800,500000,576000,921600,1000000,1152000,2000000,2500000,3000000,3500000,4000000. Device-documented4.5M/6M/10.5M and some legacy rates exceed this provider's capabilities. Destination support is checked before any baud write. Do not confuse a transport limitation with a motor limitation. No custom-baud patch or fallback transport is invented.

An optional operator-owned `CYCLO_PRODUCTS_CONFIG` defines port-only `buses` and/or identified `targets`, with independent scan/configure/discovery permissions. A target records `port`, `model`, observed `firmware`, `id`, `baud`, explicit `protocol`, optional disambiguating `catalogId`, `peerIds` for dual-axis devices, `addressingVerified` and operation permissions. No global hardware opt-in flag is required. Actual calls require a selected target and the customer command's explicit confirmation. Without a policy file, an explicitly selected port can be scanned and selected; a supplied restrictive policy is preserved. Loading the plugin performs no device access. Scans and writes default to dry run; ports, live scans and configuration require `confirmed:true` for that specific user-approved call.

Selection requires a completed bounded scan, confirmed closure/reservation release, exact candidate, verified unique addressing and explicit confirmation. For a dual-axis module both endpoints must have been observed, be explicitly paired and re-identified. Applicable EEPROM writes require both documented torque states; RAM writes check conflicting secondary listeners without requiring all secondary IDs to be inactive. Shared baud is checked on both axes. A target-specific grant cannot change protocol, catalog identity, endpoint cohort, ID or rate through selection.

All configuration defaults to dry run. Real transactions hold a cooperative bus lease, verify identity and register preconditions, snapshot state, write each requested field once and verify according to its documented reply/persistence behavior. Intentional reply suppression is reported as transmitted-unverifiable; pending persistence is distinct from completion. The compatible named API retains its narrower configuration scope. The [generic table interface](../../references/control-table-runtime.md) additionally exposes source-resolved Torque Enable, Operating Mode and goal items with item-specific prerequisites. Unknown raw addresses, reset/reboot and flashing remain unavailable. A requested profile type must match the existing Drive Mode; zero/infinite and below-resolution profiles are rejected. RGB/mask requests require explicit color/intensity. LED readback proves register state, not visible illumination under alarm/shutdown override.

Only a fully verified transition, continuity check, confirmed transport closure and released lease advances the session target. Failure/uncertainty blocks further writes; reconcile old/new locations read-only after confirming closure and verified addressing. Never repeat writes or silently roll back. The cooperative lease cannot exclude unrelated bus software; the current lease binding is Linux-specific and other platforms are unverified. Actual devices, physical serial discovery, authenticated host invocation and motor behavior remain untested.
