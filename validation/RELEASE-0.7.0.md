# Cyclo Plugin 0.7.0 validation and limits

This release replaces the two-model configuration registry with a generic identity-driven, source-bound named-capability engine. The existing fourteen Skills, Codex/Claude manifests, organization repository, original firmware MCP/SDK pin and disabled hardware defaults remain. No upstream firmware clients were relocated or changed.

## Implemented execution architecture

- One build-time compiler reads all 89 official actuator main tables and three mechanical DYD records at docs revision c88527af0888baea6f7ef3305bbbbb911b960759. Main-table factual rows retain address/width/access/memory/raw range/unit/encoding/evidence. Named capability templates add explicit ranges, enum mappings, scales, operating/firmware conditions and torque/persistence policy. Unknown semantics are not raw-write permissions. The same resolver applies to every record; no model/firmware-number whitelist remains.
- Bounded Protocol 1/2 discovery separates Ping presence, model resolution and model-specific firmware reads. Protocol 1 SDK ping's extra READ is deliberately not used to decide presence. Protocol 2 status payload retains model/firmware and the table firmware read must agree. XL-320 firmware 2, MX generation numbers, PRO R/R(A), numeric collisions1070/1080/1270, dual-axis units and Y Modbus numbers are separate cases. DYD is not an actuator.
- The customer provider uses unmodified Apache-2.0 official DynamixelSDK 3.8.4 at 0b29760ffa81d813bc749cb611a0019938c1e856 through a bounded private Python stdio adapter. Optional pyserial 3.5 belongs in an operator-chosen isolated environment. No global install or serial access was performed. Source hashes and license notices are preserved. The original Cyclo firmware SDK/MCP/CLI consumers remain intact; no competing hand-written packet implementation was added.
- All 89 records have source-bound ID/baud rows; 84 have writable LED rows. Five XW records have no LED operation. Explicit RGB/mask selection replaces implicit color guessing. 38 records have resolved shared X/MX2 paired position-profile semantics; 27 have no paired profile and 24 remain unresolved. P/PRO(A)/Y profiles are blocked for unresolved description/condition conflicts rather than given X units. No universal operation or physical support claim follows from catalog inclusion.
- Destination baud must pass the actual provider's host-rate preflight before a write. The official Python SDK does not support every motor-documented baud. ID and baud are separate transactions. Modes, torque, goals, reboot/reset and flashing remain excluded; profile interpretation must match the existing Drive Mode. Source reads never enable a device.
- Target selection binds protocol/catalog/cohort as well as port/ID/rate/model/firmware. Dual-axis selection needs both actually observed endpoints, explicit pairing/isolation, matching identities and inactive shadow IDs on both axes. Both torques are already off. Shared baud and supported snapshots are checked after transitions. Successful state advancement requires verification, confirmed closure and released lease. Failures/uncertainty invalidate targets and never trigger repeated writes or automatic rollback.

## Observed checks

The current offline suite has 322 tests:71 retained upstream firmware mocks,44 product workflow/selection/stdio regressions,138 all-catalog generic-engine cases,4 real Node-to-Python provider stdio tests over fake SDK byte ports,7 official-reader tests,5 dual-host declarations,3 retained launcher stdio tests and 50 Python checks. The all-catalog cases exercise every actuator record with ID/baud/LED capability behavior, all resolved profile templates, unrelated observed firmware numbers and deliberate failures. These are synthetic state machines, not a certification of real motors.

Python packet tests exercise the actual pinned Protocol 1/2 checksum/CRC/status parser and instruction construction over an in-memory byte port. Real serial construction raises immediately. They cover missing identity reads, error packets, unsupported protocols/broadcast and backend-rate limits. Independent row witnesses cover all 89 main tables and source positions. SDK byte hashes, manifest/frontmatter/references and packaged English-only constraints are checked. Final source/ZIP tests and native Claude CLI inventory are recorded separately.

Independent review identified and prompted corrections to profile mode 5 caller applicability, protocol/catalog/cohort permission continuity, dual-axis observed-peer selection and secondary-ID checks. Firmware-aware snapshot reads omit Drive/Profile fields before their documented availability gate. Exact-model source extraction and representative failure tests do not establish exhaustive semantic correctness of every register or firmware branch.

## Remaining boundaries

No physical port discovery, OpenRB/device connection, actuator read/write, torque/motion, flashing, robot ROS/Zenoh access, GPU training or physical deployment occurred. Default ProArt host installation and authenticated Codex/Claude Skill invocation remain unverified. Claude CLI validation/inventory is an actual isolated host CLI check, not model invocation. Firmware/model capabilities are guided by pinned published data; source conflicts/unknowns fail closed and future document changes require a reviewed regeneration.

The product lease is cooperative and currently Linux-specific. Hardware duplicate IDs cannot be excluded by Ping; operator isolation remains necessary. Some Protocol 1products document ID 253, but this release explicitly bounds unicast requests to 0..252 with the pinned SDK. No unsupported transport, arbitrary register write or hidden mode change is offered to bypass a failed capability. Organization main requires two approving reviews and signed commits; no administrator merge bypass is authorized.

Four independent Korean-intent forward evaluations were recorded as English translations in forward-review-0.7.0.md. They exercised unknown-model setup, XL-320 firmware-address correction, Y profile differences and refusal of an unobserved dual-axis peer. No critical behavior defect was observed. These are isolated agent responses, not authenticated installed-host acceptance.
